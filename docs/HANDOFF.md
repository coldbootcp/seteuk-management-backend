# 인수인계 — 세특연구소

새로 합류한 사람(또는 AI 에이전트)이 이 문서 하나로 작업을 이어받기 위한 글입니다.
프로젝트가 무엇인지는 `CLAUDE.md`가, API 계약은 `docs/API_SPEC.md`가 설명합니다.
여기서는 **지금 어디까지 와 있고, 무엇을 조심해야 하며, 다음에 무엇을 할지**만 다룹니다.

## 1. 저장소 두 개

| | 저장소 | 브랜치 | PR |
|---|---|---|---|
| 백엔드 | `coldbootcp/seteuk-management-backend` | `feat/planning-chatbot-recommendations` | #1 |
| 프론트엔드 | `coldbootcp/seteuk-management-frontend` | `feat/backend-integration` | #1 |

둘 다 `main`에 머지되지 않은 상태입니다. 두 PR은 한 쌍이라 **함께 머지해야** 합니다 —
프론트엔드는 백엔드의 새 엔드포인트(`/seteuk/uploads/latest`, `is_current`,
`period_overrides` 등)에 의존합니다.

형제 디렉토리로 나란히 두는 것을 전제합니다.

```
어딘가/
  seteuk-management-backend/
  seteuk-management-frontend/
```

## 2. 띄우는 법

### 백엔드

```bash
cd seteuk-management-backend
cp .env.example .env          # DATABASE_URL, JWT_SECRET, DEEPSEEK_API_KEY 채우기
docker compose up -d          # PostgreSQL
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`DEEPSEEK_API_KEY`가 없으면 파싱·진단·챗봇·추천이 전부 실패합니다. 이 프로젝트는
**DeepSeek만** 씁니다(Anthropic/OpenAI 키는 쓰지 않습니다 — `LLM_PROVIDER` 기본값이
`deepseek`이고, 프로바이더는 `app/services/llm/provider.py` 뒤에 있습니다).

### 프론트엔드

```bash
cd seteuk-management-frontend
cp .env.example .env.local    # NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000
npm install
npm run dev -- --port 3100
```

백엔드의 `CORS_ORIGINS`에 이 오리진이 들어 있어야 합니다(기본값에 3000·3100 포함).

### 검사

```bash
# 백엔드
uv run ruff check . && uv run pytest -q && uv run alembic check

# 프론트엔드
npx tsc --noEmit && npm test
```

백엔드 테스트는 `seteuk_test` 데이터베이스를 만들어 씁니다. **두 개를 동시에 돌리지
마세요** — 같은 DB를 drop/create 해서 서로를 깨뜨립니다(그 증상을 "테스트가 6분
걸린다"로 착각한 적이 있습니다. 단독 실행은 약 70초입니다).

## 3. 반드시 알아야 할 경계

이 프로젝트에서 값비싸게 배운 것들입니다. 어기면 같은 실수를 반복하게 됩니다.

### 프론트엔드 UI는 정본이다

통합의 목적은 **프론트엔드가 자체적으로 DeepSeek을 호출하던 것을 없애고 그 일을
백엔드가 하게 만드는 것**이지 화면을 개선하는 것이 아닙니다. 새 섹션이나 새 버튼을
만들지 말고, 정보 구조를 재배치하지 마세요. 백엔드는 스키마·엔드포인트·응답 모양을
크게 고쳐도 되지만 방향은 언제나 프론트엔드를 뒷받침하는 쪽입니다.

프론트엔드가 어떤 백엔드 기능을 쓰지 않는다는 사실은 그 자체로 결함이 아닙니다.
실제로 `plan_items`(담기 → 계획 → 완료 승격)가 UI에서 안 쓰이는 것을 결함으로 보고
'이번 학기' 화면에 계획 UI를 만들었다가 되돌렸습니다.

**다만 이미 있는 화면이 잘못 동작하는 것을 고치는 일은 여기 해당하지 않습니다.**
백엔드가 `done`을 보내는데 프론트가 `completed`와 비교해 완료가 표시되지 않던 것,
필터가 언제나 0건이던 것 같은 수정은 계속 해야 합니다. 새 UI를 만드는 것과 있는
UI를 고치는 것을 구분하는 것이 핵심입니다.

### LLM은 저자가 아니라 번역기다

한 번의 호출로 전체를 종합하게 하면 근거 없이 추상적인 문장이 나옵니다. 진단은
서로 독립적으로 계산되는 섹션들로 나뉘어 있고, 종합 평가는 원본 데이터가 아니라
앞선 섹션의 **결과만** 봅니다. 이 구조를 무너뜨리지 마세요.

### 프롬프트는 부탁이고 코드가 보증이다

프롬프트에 적은 규칙을 모델이 실제로 무시하는 것을 여러 번 관측했습니다. 지식
그래프가 계보 쌍만 돌려주던 것, 추천이 서로 같은 주제를 내던 것은 전부 결정론적
필터(`app/services/review.py`, `pipeline.py`의 `lineage_pairs`)로 막았습니다.
새 규칙을 넣을 때는 프롬프트와 코드 양쪽에 넣으세요.

### LLM에게 UUID를 베끼게 하지 않는다

실제로 한 글자를 빠뜨려(`5b5cdac2-...-fe86754a54d`, 11자리) Pydantic 검증이 배치
전체를 무효화한 사고가 있었습니다. 그 호출 안에서만 유효한 정수 index를 주고
응답의 index를 실제 id로 역참조합니다. 존재하지 않는 index는 범위 검사로 조용히
버립니다.

### 실제 키 없이 "완료"라고 하지 않는다

모킹 테스트는 스키마가 맞는 가짜 응답을 돌려주므로 **직렬화 문제와 프롬프트 품질
문제를 원리적으로 잡을 수 없습니다.** 이 프로젝트에서 실 호출로만 잡힌 결함이
십수 건입니다. LLM이 관여하는 기능을 만들면 실제 `DEEPSEEK_API_KEY`로 한 번
태워 보고 **출력 내용까지 읽고** 판단하세요.

### 테스트용 생기부

저장소의 `tmp.pdf`는 실제 학생의 생기부입니다(개인정보 포함, git 제외). 소유자가
**검증 목적으로는 항상 써도 된다**고 허락했습니다. 합성 데이터로는 안 보이는
문제가 계속 나오므로 실제로 쓰세요. 다만 이 데이터에서 나온 내용을 세션 밖으로
내보내는 것(공개 게시 등)은 별개입니다.

### 출결은 화면에 노출하지 않는다

출결(`attendance`)은 생기부에서 파싱해 저장하지만 **어떤 탭에도 보여주지
않습니다.** 챗봇이 개인화된 답을 만들 때 참고하는 재료로만 존재합니다(소유자 결정).
"출결이 화면에 없다"를 결함으로 보고하지 마세요. 확인할 곳은
`app/services/chat/context.py`입니다.

## 4. 네 개의 층을 섞지 않는다

| 층 | 뜻 | 개수 |
|---|---|---|
| `roadmap_nodes` | 학기 서사 마디 — "이 학기에 무엇을 향해 가는가" | 6개 고정 |
| `roadmap_plan_events` | 그 마디가 제안하는 주제 후보 | 마디당 10개 |
| `plan_items` | 실제로 하기로 한 것 | 자유 |
| `activities` 등 | 일어난 일 | 자유 |

담기(`POST /roadmaps/plan-events/{id}/adopt`)가 제안을 계획으로 바꾸고, 완료가
계획을 기록으로 바꿉니다. **담아도 제안은 지워지지 않습니다** — "무엇을
제안했는가"와 "무엇을 하기로 했는가"는 다른 사실입니다.

한 가지 더: 마디의 `status`는 **진척**(planned/active/partial/done/skipped)이고,
"학생이 지금 어느 학기에 있는가"는 응답의 `is_current`가 답합니다. 두 개념을 섞으면
이번 학기 목표를 일찍 달성한 학생에게 화면이 "지금은 다음 학기"라고 말하게 됩니다.

## 5. 지금 상태

### 검증한 것

실제 생기부와 실제 DeepSeek 키로 전 구간을 태웠습니다.

가입 → 온보딩 3단계 → 로드맵 확정 → 생기부 업로드 → 검토·카테고리별 반영 →
흐름 맵 반영 → 진단(학기 리뷰·성적 추이·진로 사슬·활동 인벤토리·지식 그래프·SWOT)
→ 활동 저장 → 정합 판정 → AI 검토 → 챗봇(일반·수정) → 후속 추천 → 담기 →
완료 승격 → 2단계 계보 → 로그아웃·재로그인.

백엔드 테스트 200개, `ruff`, `alembic check` 통과. 프론트엔드 `tsc`, `npm test` 통과.

### 검증하지 못한 것

- **카카오 소셜 로그인** — 코드는 붙였지만 실제 카카오 앱 키가 없어 미검증입니다.
  프론트엔드 `.env.local`에 `NEXT_PUBLIC_KAKAO_JS_KEY`를 넣으면 로그인 화면에
  버튼이 나타납니다(키가 없으면 버튼 자체를 그리지 않습니다).
- **파서는 실제 샘플 1건 기준**입니다. 다른 학교·연도 양식에서는 재조정이 필요할
  수 있습니다.

## 6. 다음에 할 만한 일

우선순위 순으로 적었지만, 소유자의 판단이 우선입니다.

1. **두 PR을 함께 머지** — 서로 의존하므로 한쪽만 머지하면 깨집니다.
2. **비동기 job을 워커 큐로 분리** — 파싱·진단이 FastAPI BackgroundTasks에 묶여
   있어 배포할 때마다 진행 중인 job이 죽습니다. 지금은 기동 시
   `STALE_JOB_TIMEOUT_MINUTES`를 넘긴 행을 실패로 확정해 사용자가 재시도할 수
   있게만 해 두었습니다. Celery/ARQ 등으로 옮기는 것이 정공법입니다.
3. **로드맵·후속 추천을 job 패턴으로** — 동기 호출이라 20~40초 걸립니다. 클라이언트
   타임아웃이 문제가 되면 진단과 같은 방식으로 옮기세요.
4. **후속 추천의 화면 경로** — 백엔드(`POST /recommendations/follow-up`, `adopt`)는
   완성됐고 테스트도 통과하는데 프론트엔드가 호출하지 않습니다. 화면을 만들지
   않는다는 경계 때문에 남겨 두었으니, **소유자에게 먼저 물어보세요.**
5. **진단 상세 화면** — `semester_reviews`, `grades_trend`, `activity_inventory`,
   `knowledge_graph_links`, `opportunities`가 계산만 되고 화면에 나오지 않습니다.
   이것도 UI 추가라 소유자 확인이 먼저입니다.
6. **미래 학년 규칙의 범위** — 현재 학년보다 뒤 시점을 막는 규칙이 생기부 파싱
   경로에만 있습니다. 탭 직접 입력(`POST /activities`)과 계획 완료 승격에는 없어서
   2학년 학생이 3학년 활동을 만들 수 있습니다. 넓힐지는 제품 판단입니다.

## 7. 시간을 많이 쓴 함정들

같은 곳에서 헤매지 않도록 적어 둡니다.

- **백엔드와 프론트엔드의 값이 다른 이름을 쓰는 경우가 있었습니다.** 계획 상태는
  `done`인데 프론트가 `completed`와 비교했고, 성적은 `achievement_grade`인데
  `achievement`를 읽었습니다. 후자 때문에 성적 32건이 검토 화면에 한 건도 오르지
  못했습니다. **타입은 손으로 적지 말고 `npx openapi-typescript
  http://127.0.0.1:8000/openapi.json -o lib/api-types.ts`로 재생성하세요.**
- **화면의 카테고리와 백엔드의 영역은 1:1이 아닙니다.** 이름에 "봉사"가 든 활동은
  봉사 탭에 보이지만 `activities` 영역에 있습니다. 검토 화면이 카테고리별로
  반영하므로, 한 카테고리만 보내면 백엔드가 그 영역을 "이게 전부"로 읽고 앞서
  반영한 것을 지웁니다.
- **파서가 "N학기"라는 글자를 학기 구분으로 읽으면 안 됩니다.** 성적표 열
  머리글(`교과 / 과목 / 1학기 / 2학기 / 비고`)과 본문 표현("1학기의 후속 연구로")이
  전부 걸립니다. 제 줄에 홀로 서 있고 짝이 옆에 붙어 있지 않은 것만 인정합니다
  (`app/services/parser/anchors.py`의 `semester_markers`).
- **생기부의 세특은 학기를 나누지 않습니다.** 과목당 한 덩어리로 쓰여 있어 어느
  활동이 몇 학기인지 문서가 말해 주지 않습니다. 파서는 지어내지 않고 비워 두고,
  검토 화면에서 학생이 고른 값을 `period_overrides`로 받습니다. 성적은 다릅니다 —
  표에 1학기/2학기 열이 있어 학기가 분명합니다.
- **`useEffect` 안에서 `useState`로 "이미 했는지"를 표시하면 자기 요청을 스스로
  취소합니다.** 상태 변경 → 리렌더 → cleanup → `cancelled = true`. 그런 플래그는
  `useRef`로 두세요.
- **바깥 시계(오늘 날짜)를 기준점으로 쓰지 마세요.** 생기부는 몇 해 전 문서일 수
  있습니다. 수상의 학년은 문서 안의 `참가대상`에서, 학기는 수상연월일에서 읽습니다.

## 8. 사람이 결정해야 하는 것

임의로 바꾸지 말고 소유자에게 물어보세요.

- 새 화면·새 버튼을 만드는 일 전부(위 4·5번 포함)
- 미래 학년 규칙을 수동 입력 경로까지 넓힐지
- **대학 적합도·전형 추천 기능** — 실제 대학별 내신 산출식·커트라인 데이터가 없어
  만들면 LLM이 그럴듯한 대학명과 점수를 지어냅니다. 의도적으로 제외했습니다.
- 챗봇 수정 모드에 삭제 도구를 넣는 일 — 대화 중 오해로 3년치 기록이 사라지는
  사고를 막기 위한 의도적 제약입니다. 삭제는 탭의 DELETE로만 합니다.
