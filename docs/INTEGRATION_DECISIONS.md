# 백엔드 ↔ seteuk-management-frontend 통합 — 충돌 사안과 결정 목록

`20260826backend`(FastAPI/Postgres)를 `coldbootcp/seteuk-management-frontend`
(`seteuk-personalization-prototype` v0.7.0)에 통합하기 전에 정해야 할 것들입니다.

각 항목의 `결정:` 칸을 채워 주시면 그대로 진행합니다.

---

## 0. 먼저 알아야 할 것 — 이건 프론트+백엔드가 아닙니다

프론트엔드 리포는 **자체 완결 제품**입니다. Cloudflare Workers 위의 Next.js 16이고,
**자기 DB(D1)** 와 **자기 DeepSeek 하네스**를 갖고 있으며, 온보딩·로드맵·활동·성적·
추천이 전부 `app/api/*`에 TypeScript로 구현돼 있습니다.

백엔드를 쓰지 않습니다. 외부 API 의존은 딱 두 곳뿐이고, 그마저도 **옛
`seteuk-ai` 파이썬 프로토타입**을 가리킵니다.

```
POST /analyze          ← 생기부 파싱      (lib/seteuk-api.ts)
GET  /status/{taskId}  ← 파싱 상태
```

즉 지금 두 시스템은 **같은 문제를 각자 푼 두 개의 제품**입니다. 통합은 병합이 아니라
**어느 쪽 모델이 이길지 고르는 일**입니다. 아래가 그 목록입니다.

---

## 1. 반드시 하나를 골라야 하는 것 (구조적 충돌)

### D-1. 로드맵 모델 — 평면 계획 vs 서사 노드

두 모델이 같은 것을 다르게 표현합니다. 공존할 수 없습니다.

| | 백엔드 | 프론트엔드 |
|---|---|---|
| 구조 | `plan_items` 한 테이블 (평면) | `roadmaps`(버전) → `roadmap_nodes`(순서·서사단계) → `roadmap_plan_events`(월/일) |
| 생성 근거 | 학생의 진단 결과에서 생성 | **서사 템플릿**(반도체 v1)을 학생에 맞게 개인화 |
| 재생성 | 손대지 않은 AI 계획만 교체 | 이전 버전을 `superseded`로 남기고 새 버전 |
| 세분화 | 학기 단위 | 학기 노드 + 월/일 단위 이벤트 |
| 계보 | `source_activity_id`로 과거 활동에 매달림 | `instantiated_activity_id`로 노드↔활동 연결 |

프론트엔드 쪽이 더 풍부합니다(버전 관리, 서사 단계, 월 단위, 역량 목표). 백엔드 쪽은
더 단순하고 진단과 직접 이어져 있습니다.

### D-2. 활동과 계획을 잇는 방식 — 계보 vs 정합(Reconciliation)

“이 활동이 계획의 어디에 해당하는가”를 양쪽이 다르게 답합니다.

- **백엔드**: 활동 → 이전 활동 (`parent_activity_id`). 3년치가 하나의 사슬이 됩니다.
  계획을 완료하면 그 활동의 자식으로 승격됩니다.
- **프론트엔드**: 활동 → 로드맵 노드. 저장 시 `MATCH` / `PARTIAL_MATCH` / `DIVERGE` /
  `MISS` / `UNCLASSIFIABLE`로 판정하고 이유·조치·신뢰도를 `reconciliation_logs`에 남깁니다.

둘은 배타적이지 않습니다 — 활동이 `parent_activity_id`와 `roadmap_node_id`를 **둘 다**
가질 수도 있습니다. 다만 그러면 “고도화 사슬”과 “로드맵 진척”이라는 두 축을 동시에
관리해야 하고, UI에서 어느 쪽을 주로 보여줄지 정해야 합니다.

> **결정:** _(하나만? 둘 다? 둘 다면 어느 쪽이 주 화면?)_

### D-3. 성적 모델 — 생기부 형태 vs 로드맵 종속

- **백엔드** `academic_performance`: 생기부 그대로 — `units`, `achievement_grade`,
  `raw_score`, `subject_average`, `std_deviation`, `rank`, `category`.
  진단의 `grades_trend`(LLM 없는 순수 데이터 차트)가 여기서 나옵니다.
- **프론트엔드** `student_semester_courses` + `student_course_grades`:
  과목이 **`roadmap_node_id`에 매달려** 있고, 성적은 `rank`/`score`/`note`뿐입니다.

프론트엔드 구조로는 백엔드의 성적 추이 차트를 만들 수 없습니다(표준편차·과목평균·
성취도가 없음). 반대로 백엔드 구조에는 “이 과목이 어느 로드맵 노드에 속하는가”가 없습니다.

### D-4. 기록 범위 — 6개 탭 vs 활동 중심

백엔드에만 있는 것: **독서 · 수상 · 봉사 · 출결**, 그리고 생기부 형태의 성적.
프론트엔드에만 있는 것: **첨부파일**(R2 + 추출 텍스트), **수행평가 안내문 분석**,

### D-5. 정본 데이터베이스 — D1 vs Postgres

프론트엔드가 D1을 계속 쓰면 **진실의 원천이 둘**이 됩니다(가장 피해야 할 상태).
그런데 **Cloudflare Workers는 일반 TCP Postgres 연결을 열 수 없습니다.** 선택지는:

- (a) D1을 버리고 프론트엔드는 백엔드 HTTP API만 호출 — 가장 깨끗, 대신 프론트엔드의
  `app/api/*`와 Drizzle 스키마 상당 부분을 들어냄
- (b) Postgres를 정본으로 두고 Workers에서 **Hyperdrive**로 접속 — 인프라 추가
- (c) 백엔드를 버리고 D1로 통일 — 파서·진단·챗봇을 전부 TypeScript로 다시 씀
- (d) 둘 다 유지하고 동기화 — 권장하지 않습니다

> **결정:** _(추천은 (a)입니다)_

### P-4. 인증 주체 — JWT/카카오 vs ChatGPT 헤더

- 백엔드: 자체 JWT(access/refresh) + 카카오 소셜 로그인 + `refresh_tokens` 테이블.

여기가 가장 설계가 필요한 지점입니다. ChatGPT 안에서 돈다면 백엔드가 그 신원을 어떻게
신뢰할지(토큰 교환) 설계해야 하고, 웹앱으로도 쓸 거라면 두 인증 경로를 함께 지원해야 합니다.

## 4. 통합하면 얻는 것

각자 상대에게 없는 자산이 분명합니다.

**백엔드가 가진 것** — 검증된 생기부 파서, 8개 섹션 진단(성적 추이·학기 리뷰·진로
사슬·활동 인벤토리·지식 그래프·SWOT), 활동 계보, SSE 챗봇 13개 도구, JWT/카카오 인증,

루프, Reviewer 단계, append-only 피드백 신호, 첨부파일 + 수행평가 안내문 분석,
엣지 배포.

## 5. 제가 보기에 가능한 형태

**시나리오 A — 백엔드를 정본으로, 프론트엔드는 화면만 (추천)**
D1과 `app/api/*`의 도메인 로직을 걷어내고 FastAPI를 유일한 진실의 원천으로 둡니다.
프론트엔드의 로드맵 UX·Reviewer·피드백은 백엔드 쪽에 기능으로 옮깁니다.
가장 깨끗하지만 프론트엔드 코드를 많이 들어냅니다.

**시나리오 B — 역할 분담**
백엔드는 기록·파싱·진단·챗봇, 프론트엔드는 로드맵·정합·추천을 각자 소유하고
HTTP로 붙입니다. 코드를 덜 버리지만 **활동 데이터가 양쪽에 존재**하게 되어 D-5의
“진실의 원천 둘” 문제를 정면으로 맞습니다.

**시나리오 C — 프론트엔드를 정본으로**
백엔드는 파싱 서비스로만 축소하고 나머지를 TypeScript로 다시 씁니다.
진단·챗봇·계보를 다시 만들어야 해서 비용이 가장 큽니다.

## ※1. D-2가 CLAUDE.md의 핵심 원칙과 충돌합니다

정합을 정본으로 삼는 것과 별개로, `activities.parent_activity_id`(활동 계보)를
없애면 다음이 전부 무너집니다.

- 진단의 `career_thread` (과거 활동이 이어지는 진로 사슬)
- 진단의 `knowledge_graph_links` (계보 쌍을 제외하는 필터의 기준)
- `GET /activities/{id}/lineage`
- CLAUDE.md의 명시 원칙: *"활동 계보를 끊지 않는다"*, 그리고
  *"계획 → 실행 → 기록 → 다음 계획 루프와 활동 계보가 범용 LLM과의 차별점"*

두 링크는 서로 다른 질문에 답합니다.

- `parent_activity_id` — **이 활동이 어떤 활동을 고도화한 것인가** (과거 축)
- 정합 판정 — **이 활동이 로드맵의 어느 노드를 충족했는가** (계획 축)

**권고**: 정합을 계획 축의 정본으로 삼되 `parent_activity_id`는 유지한다.
활동은 두 링크를 모두 가질 수 있고, 주 화면은 로드맵 진척, 진단은 계보를 읽는다.

## ※2. D-3과 D-4가 부분적으로 충돌합니다

D-4에서 "생기부 형태 성적을 유지"하기로 했는데, D-3의 프론트엔드 성적 모델
(`rank`/`score`/`note`)에는 진단의 성적 추이 차트에 필요한 값이 없습니다 —
`raw_score`, `subject_average`, `std_deviation`, `achievement_grade`, `units`.

**권고**: 성적 *레코드*는 백엔드 `academic_performance`를 유지하고(생기부 파싱 결과가
그대로 들어가며 차트가 살아남음), 프론트엔드가 가져온 것은 **연결**만 취한다 —
즉 `academic_performance`에 nullable `roadmap_node_id`를 추가해

## ※4. 성적 추이 그래프 (2026-09-04 확정)

**학기별 석차등급 평균 한 줄만 그린다.**

- 매 학기 석차등급이 **있는** 과목만 평균 낸다.
- 석차등급이 없는 과목(진로선택·전문교과·P과목 — 실제 샘플에서 145행 중 36행,
  약 25%)은 **평균에서 제외하고 화면에도 넣지 않는다.**
- 과목별 개별 선은 그리지 않는다. 성취도를 등급으로 환산하지 않는다.
- Y축은 1등급이 위(낮을수록 좋음).

따라서 `grades_trend`의 `subjects[]`(과목별 시계열)는 제거되고 `overall[]`만 남으며,
값은 `average_raw_score`가 아니라 **학기별 평균 석차등급**이 된다.
