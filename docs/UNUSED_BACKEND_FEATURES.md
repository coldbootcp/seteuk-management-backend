# 백엔드에 구현되어 있지만 프론트엔드가 쓰지 않는 것들

`app/api/v1/*.py`의 엔드포인트 59개와 `seteuk-management-frontend/lib/workspace-adapter.ts`
(모든 백엔드 호출이 지나가는 유일한 통로)·`lib/api-client.ts`·`lib/chat.ts`·
`app/chat-view.tsx`를 대조해서 만들었다. UI 형태를 바꾸는 일은 이제 허용되지만
(`docs/HANDOFF.md` 3절), 무엇을 화면으로 옮길지는 여전히 제품 판단이라 — 이 문서는
**어디에 무엇이 비어 있는지 지도**만 그린다. 결정은 소유자의 몫이다.

## 어떻게 확인했는지

`workspace-adapter.ts`의 `handleLegacyRoute` 함수 하나가 화면이 부르는 모든
`/api/...` 경로를 실제 백엔드 `/api/v1/...` 호출로 옮기는 유일한 통로다. 이 파일을
전부 읽고 그 안에서 실제로 나가는 `api(...)` 호출을 전부 뽑은 뒤, 백엔드 라우터
전체와 하나씩 대조했다. 인증(`api-client.ts`)과 챗봇 스트리밍(`chat.ts`,
`chat-view.tsx`)은 이 파일을 거치지 않고 자체적으로 호출하므로 따로 확인했다.

---

## 1. 진단을 실행할 방법이 화면에 없다

**가장 근본적인 gap이다.** `POST /diagnosis`(`diagnosis_service.create_diagnosis` +
백그라운드 job)를 부르는 코드가 프론트엔드 어디에도 없다. `GET /diagnosis/latest`만
불러서 이미 있는 결과를 보여줄 뿐이다.

즉 **실제 사용자는 자기 진단을 스스로 돌릴 방법이 없다.** 지금 화면에 진단 결과가
보인다면 그건 개발 중에 API를 직접 호출해 만들어 둔 데이터를 우연히 보고 있는
것이지, 그 학생이 버튼을 눌러서 생긴 결과가 아니다. "진단"이라는 낱말 자체가
`app/workspace-app.tsx`에는 플레이스홀더 문구("의료 AI 진단 모델…") 말고는 등장하지
않는다.

같은 이유로 사전질문 흐름도 통째로 비어 있다.

| 엔드포인트 | 뜻 |
|---|---|
| `POST /diagnosis` | 진단 job을 시작한다(처음 한 번, 이후엔 생략 가능) |
| `GET /diagnosis/pre-questions` | 생기부-답변 갭을 물어보는 사전질문(최초 1회) |
| `POST /diagnosis/pre-questions/answers` | 사전질문 답변 제출 — `student_interests`에 반영됨 |
| `GET /diagnosis/{id}` | 특정 진단(최신이 아닌 것)을 다시 조회 |

**영향**: `toDna()`가 읽는 career_thread/strengths/weaknesses/threats/headline은
전부 이 job이 만든 결과다. 실행 버튼이 없으면 그 뒤에 이어지는 모든 진단 관련 화면
(2절)도 실제로는 절대 채워지지 않는다.

---

## 2. 진단이 계산하는 것의 절반 이상이 화면에 안 나온다

`toDna()`(`workspace-adapter.ts:176`)는 `DiagnosisResult`에서 딱 다섯 개만 읽는다:
`career_thread`, `strengths`, `weaknesses`(→gaps), `threats`(→riskFlags),
`headline_comment`. 백엔드가 계산하는 나머지는 전혀 안 쓰인다.

| 필드 | 뜻 | 계산 방식 |
|---|---|---|
| `semester_reviews` | 학기당 성적/독서/활동 3종 리뷰 텍스트 | 학기별 1회 LLM 호출, 그 학기 원자료만 봄 |
| `grades_trend` | 과목별 시계열 + 학기별 평균 등급 | **LLM 없이** 순수 계산, 차트용 |
| `activity_inventory` | 활동 전량을 역량×심화도 축으로 분류 | 학년 단위 배치 호출 |
| `knowledge_graph_links` | 활동 간 숨은 연결(계보로는 안 잡히는 것) | 활동 전체를 LLM에 통째로 주고 판단 |
| `opportunities` | SWOT의 O(강점·약점과 별개) | 종합 평가 호출의 일부 |

`grades_trend`는 특히 아까운 손실이다 — **LLM 호출이 필요 없는 순수 데이터**라
비용 없이 바로 차트로 그릴 수 있는데 계산까지 다 해 놓고 버려진다.

**영향**: 소유자가 "학교 생기부 컨설팅 업체" 수준으로 설계해 달라고 요청해 만든
SWOT·활동 인벤토리·지식 그래프가 전부 이 상태다. 진단 파이프라인이 실제로 하는 일의
절반 이상이 사용자에게 한 번도 보이지 않는다.

## 3. 후속 추천 기능 전체가 화면에서 완전히 끊겨 있다

`POST /recommendations/follow-up`(활동 하나의 계보 전체 + 최신 진단을 근거로
난이도가 다른 선택지 3개를 만드는 것)를 부르는 코드가 없다. 그 아래로 이어지는
조회·담기·피드백도 전부 마찬가지다.

| 엔드포인트 | 뜻 |
|---|---|
| `POST /recommendations/follow-up` | 후속 추천 생성(동기 호출, 20~40초) |
| `GET /recommendations` | 추천 이력 목록 |
| `GET /recommendations/{id}` | 추천 하나 상세 |
| `POST /recommendations/{id}/adopt` | 선택지를 계획으로 담기 — "추천 → 계획 → 실행 → 기록" 루프를 닫는 지점 |
| `POST /recommendations/{id}/feedback` | 담았는지/관심 없는지 기록(덮어쓰지 않고 누적) |
| `GET /recommendations/feedback/history` | 피드백 이력 |

흥미로운 점: `workspace-adapter.ts`에 `/api/recommendation-feedback` 케이스가
남아 있어서 `POST /recommendations/{id}/feedback`으로 연결까지 되어 있다. 하지만
그 케이스를 실제로 호출하는 UI 코드가 화면 어디에도 없다 — **어댑터는 준비돼
있는데 그 문을 여는 버튼이 없는** 상태다. 예전 프론트엔드(수행평가 분석 UI,
`AssignmentAnalysis.recommendations`)가 쓰던 자리의 흔적으로 보이는데, 그 기능
자체는 "수행평가 안내문 분석은 빼라"는 지시로 제외됐다.

**영향**: 활동 하나를 완료해도 "다음엔 뭘 하지?"를 AI가 제안하는 이 서비스의
두 번째 핵심 기능(기능2)이 사용자에게 전혀 닿지 않는다.

---

## 4. 계획(`plan_items`) 계층이 화면에서 완전히 분리돼 있다

이건 한 번 UI로 옮겼다가 사용자 지시로 되돌린 이력이 있다("프론트엔드 UI를 바꾸지
말라"는 통합 기간 제약 — 지금은 해제됨, `docs/HANDOFF.md` 참고). 되돌린 뒤로 다시
손대지 않아서 지금도 비어 있다.

| 엔드포인트 | 뜻 |
|---|---|
| `GET /plans` | 계획 목록 |
| `POST /plans` | 계획 직접 생성 |
| `GET /plans/{id}` · `PATCH /plans/{id}` · `DELETE /plans/{id}` | 계획 조회/수정/삭제 |
| `POST /plans/{id}/complete` | **계획 → 기록 승격** — 활동/독서 탭에 실제 행을 만들고 계보를 잇는 지점 |
| `POST /roadmaps/plan-events/{id}/adopt` | 로드맵 제안 → 계획으로 담기 |
| `GET /roadmaps/nodes/{id}/plans` | 그 마디에 담긴 계획 목록 |

챗봇의 수정 모드는 이 계층을 도구로 직접 건드릴 수 있으므로(대화로 계획을 만들고
완료 승격할 수 있음), **완전히 죽은 기능은 아니다** — 다만 챗봇을 거치지 않고는
학생이 스스로 계획을 만들거나 완료 처리할 화면상 방법이 없다.

**영향**: CLAUDE.md가 이 서비스의 정체성으로 못박은 "계획 → 실행 → 기록 → 다음
계획" 루프에서, 계획을 세우는 절반이 챗봇에만 있고 탭에는 없다.

## 5. 활동 계보(3년 연결) 조회가 화면에 없다

`GET /activities/{id}/lineage` — 활동 하나에서 뿌리까지 거슬러 올라간 뒤 후손
활동과 아직 실행 안 된 계획까지 한 사슬로 돌려주는 엔드포인트. 프론트엔드
어디에서도 부르지 않는다.

**영향**: CLAUDE.md는 "활동 계보를 끊지 않는다"를 개발 원칙으로 명시하고, 챗봇
수정 모드가 `parent_activity_id`를 스스로 채우는 것까지 검증했을 만큼 이 서비스의
핵심 차별점으로 강조한 개념이다. 데이터는 정확히 쌓이고 있는데(활동을 만드는 모든
경로가 `parent_activity_id`/`source_activity_id`를 채운다), **그 사슬을 한눈에
보여주는 화면 자체가 없다.**

## 6. 원본 파일 두 종류를 내려받을 수 없다

| 엔드포인트 | 뜻 | 상태 |
|---|---|---|
| `GET /activities/attachments/{id}/file` | 활동에 첨부한 파일 원본 | UI에 `<a href="/api/activity-files/{id}">`로 다운로드 링크가 **있지만 죽어 있다** — 이 프로젝트는 Next.js API 라우트가 하나도 없는 순수 클라이언트 SPA라서, 이 링크는 실제 브라우저 내비게이션이 되는 순간 404가 난다(`jsonRequest`를 거치는 호출만 어댑터가 가로챈다). |
| `GET /seteuk/uploads/{id}/file` | 업로드한 생기부 PDF 원본 | UI에 다운로드 시도 자체가 없다. |

**영향**: 첨부파일 다운로드는 "버튼은 있는데 눌러도 안 됨"이라 사용자가 버그로
느끼기 쉽다 — 이 문서의 항목 중 유일하게 **눈에 보이는 깨진 UI**다.

## 7. 로드맵의 옛 경로(`/plans/roadmap`)가 새 경로(`/roadmaps`)로 대체됐다

`POST /plans/roadmap`은 Phase 4(선행 구현)에서 만든 "진단·활동·기존 계획을 근거로
남은 학기 계획을 만드는" 원래 로드맵 생성 방식이다. 프론트엔드 통합 이후 이 자리는
`POST /roadmaps`(6개 마디짜리 서사 로드맵 + `roadmap_plan_events`)로 대체됐고,
프론트엔드는 오직 `/roadmaps` 쪽만 부른다.

**다른 항목들과 성격이 다르다** — "아직 못 붙인 기능"이 아니라 **설계가 바뀌면서
남은 이전 세대 엔드포인트**다. `GET /plans/roadmap-overview`도 이 옛 계층
(`plan_items`를 과거/현재/미래로 재배치하는 조립 엔드포인트)에 속해 있어 함께
안 쓰인다. 지우거나 유지할지는 "이 옛 방식이 여전히 유효한 대안 경로인가,
아니면 죽은 코드인가"를 소유자가 판단할 문제다.

---

## 8. 그 밖의 자잘한 것들

- **`GET /roadmaps/{id}`** — 특정 로드맵(과거 버전 포함)을 id로 조회. `GET
  /roadmaps/active`(현재 버전)만 쓰이고, 지난 버전을 들여다보는 화면은 없다.
- **`DELETE /conversations/{id}`** — 대화 목록 조회·새 대화 시작은 되지만 대화를
  지우는 UI는 없다.
- **출결 CRUD(`/attendance`)** — 이건 gap이 아니라 **의도된 설계**다. 출결은
  화면에 노출하지 않고 챗봇 컨텍스트로만 쓰기로 확정했다(`docs/HANDOFF.md`
  참고). 목록에 넣은 이유는 완전성 때문이지, 손볼 대상이라서가 아니다.

---

## 반대 방향: 프론트엔드에만 있고 백엔드가 받쳐주지 않는 것

이 문서의 주제는 아니지만 대조하다 발견했다. `lib/product-harness.ts`의
`AssignmentAnalysis` 타입(`recommendations` 필드 포함, "수행평가 분석" 개념)은
백엔드에 대응하는 기능이 전혀 없고, `loadWorkspace()`는 `latestAnalysis: null`을
항상 고정으로 돌려준다. 사용자가 "수행평가 안내문 분석은 빼라"고 명시적으로
제외한 기능의 흔적이라, 정리해도 되는 죽은 타입이다.

## 요약

| 구역 | 상태 |
|---|---|
| 진단 실행(1) | **트리거 자체가 없음** — 가장 시급 |
| 진단 상세 5종(2) | 계산은 되는데 표시 안 됨 |
| 후속 추천 전체(3) | 완전히 끊김(피드백 배선만 남아 있음) |
| 계획 탭(4) | 챗봇으로만 가능, 탭에는 없음 |
| 활동 계보 화면(5) | 데이터는 있는데 볼 화면이 없음 |
| 파일 다운로드(6) | 첨부파일은 깨진 링크, 원본 PDF는 아예 없음 |
| `/plans/roadmap` 계열(7) | 신·구 설계 공존, 정리 여부 판단 필요 |
| 기타(8) | 대화 삭제 UI 없음, 옛 로드맵 버전 조회 없음 |

우선순위를 매긴다면: **1(진단 실행) → 3(후속 추천) → 2(진단 상세) → 6(다운로드
링크 수정)** 순이 서비스의 핵심 루프("기록 → 진단 → 계획 → 실행")를 살리는 데
효과가 크다. 4·5는 챗봇이 이미 부분적으로 대신하고 있어 상대적으로 급하지 않고,
7·8은 정리 성격이 강하다.
